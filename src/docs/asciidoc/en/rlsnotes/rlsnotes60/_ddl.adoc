[#rnfb60-ddl-tbl-create-select]
== `CREATE TABLE ... AS <subquery>`
Adriano dos Santos Fernandes

Tracker ticket: https://github.com/FirebirdSQL/firebird/issues/1181[#1181]

Tables can now be created and optionally populated based on a query expression.

[listing,subs=+quotes]
----
CREATE [{GLOBAL | LOCAL} TEMPORARY] TABLE
  [IF NOT EXISTS] [_tbl-schema_ <period>] _tablename_
  <as-subquery-clause>
  [{<table_attrs> | <gtt_table_attrs>}]

RECREATE [{GLOBAL | LOCAL} TEMPORARY] TABLE
  [_tbl-schema_ <period>] _tablename_
  <as-subquery-clause>
  [{<table_attrs> | <gtt_table_attrs>}]

<as-subquery-clause> ::=
  [ (_colname_ [, _colname_ ...]) ]
  AS { (<query-expression>) | <query-expression> }
  [WITH [NO] DATA]
----

[NOTE]
====
The syntax supported by Firebird has two deviations from the SQL standard syntax:

* the parentheses around the _query-expression_ are optional
* the `WITH [NO] DATA` clause is optional, defaulting to `WITH DATA`
====

The table columns are derived from the query select list.
If a column name list is specified, it must have the same number of columns as the query result.
Otherwise, column names are taken from the query output names.
Unnamed expressions must be explicitly aliased.

[horizontal.compact]
`WITH DATA`::
(default) creates the table and inserts the query result into the newly created table, in the same transaction
`WITH NO DATA`::
creates only the table

For global and local temporary tables, normal temporary-table data lifetime rules apply.
Package temporary tables do not support this syntax.

It is not possible to create an external table using the `CREATE TABLE ... AS <subquery>` syntax.

[#rnfb60-ddl-tbl-create-select-type]
=== Datatypes and Domains

When a select list item is a direct reference to a source table or view column, the new column copies the source column's exact datatype instead of one derived only from the query result (which would lose information such as declared `NUMERIC`/`DECIMAL` precision).

* If the source column is based on a named domain, the new column references that domain directly, as if it had been declared `_colname_ <domain>`.
However, if the column appears in an outer join context -- where it is nullable -- and the domain is declared `NOT NULL`, the new column instead uses a copy of the domain's underlying type (preserving precision, scale, character set, collation, etc.) without referencing the original domain.
* If the source column is based on an auto-generated (implicit) domain, its exact type (precision, scale, character set, collation, etc.) is copied.

For any other select list item (e.g. an expression, including literals or aggregates), the new column's datatype is derived from the query result.

[#rnfb60-ddl-tbl-create-select-charset]
==== Character Sets

For `CHAR` and `VARCHAR` columns not covered by the direct column-reference rule above, the database default character set is *not* used.
The character set and collation of the new column are copied from the corresponding expression in the query.

String literals use the connection character set, so columns created from string literals inherit the connection character set.

[#rnfb60-ddl-tbl-create-select-exmpl]
=== Examples

[listing]
----
CREATE TABLE employee_copy AS
  SELECT emp_no, first_name, last_name
  FROM employee;

CREATE TABLE employee_names (id, full_name) AS
  SELECT emp_no, first_name || ' ' || last_name
  FROM employee
  WITH NO DATA;

CREATE GLOBAL TEMPORARY TABLE session_report AS
  (employee_number, salary)
  SELECT emp_no, salary
  FROM employee
  WITH DATA
  ON COMMIT PRESERVE ROWS;

CREATE LOCAL TEMPORARY TABLE tx_work AS
  (SELECT emp_no, salary
   FROM employee)
  WITH NO DATA;

CREATE TABLE high_salary AS
  (WITH avg_salary AS (
     SELECT AVG(salary) AS avg_salary
     FROM employee)
   SELECT e.emp_no, e.salary
   FROM employee e, avg_salary a
   WHERE e.salary > a.avg_salary);
----

[#rnfb60-ddl-tbl-create-select-isql]
=== ISQL behavior

ISQL in AUTODDL mode (the default) uses separate transactions for DDL and DML statements.
When `CREATE TABLE ... AS <subquery>` is executed with `WITH DATA`, the table creation and data population occur in the DDL transaction.

For regular tables, the inserted rows are not visible to the DML transaction until the DDL transaction is committed.
For temporary tables with `ON COMMIT DELETE ROWS`, this behaviour is even more surprising because the rows belong to the DDL transaction and are therefore not visible to the DML transaction at all.

For example:

[source]
----
SQL> CREATE TABLE T1 AS SELECT 1 A FROM RDB$DATABASE;
SQL> SELECT * FROM T1;

SQL> COMMIT;
SQL> SELECT * FROM T1;

           A
============
           1
----

With a temporary table:

[listing]
----
SQL> CREATE GLOBAL TEMPORARY TABLE T1 AS SELECT 1 A FROM RDB$DATABASE;
SQL> SELECT * FROM T1;

SQL> COMMIT;
SQL> SELECT * FROM T1;
----

The table exists, but no rows are returned because the data was inserted in the DDL transaction and is not visible to the DML transaction.

To avoid this behaviour, disable AUTODDL before executing the statement:

[listing]
----
SQL> SET AUTODDL OFF;

SQL> CREATE GLOBAL TEMPORARY TABLE T1 AS SELECT 1 A FROM RDB$DATABASE;
SQL> SELECT * FROM T1;

           A
============
           1
----

When AUTODDL is disabled, table creation and data population occur in the current transaction, making the inserted rows immediately visible.

Like DDL for "`normal`" tables, the DDL for LTTs is <<rnfb60-engine-ltt-ddl-tr,transactional>>.

Consult the Firebird 6.0 Language Reference for the full DDL syntax. +

For more information on created Local Temporary Tables, see als <<rnfb60-engine-ltt>>.

[#rnfb60-ddl-ltt-create]
=== `CREATE LOCAL TEMPORARY TABLE`

[listing,subs=+quotes]
----
{CREATE | RECREATE} LOCAL TEMPORARY TABLE [IF NOT EXISTS]
  [_tbl-schema_ <period>] _tablename_
  (<column definitions>)
  [ON COMMIT {DELETE | PRESERVE} ROWS]
----

The `ON COMMIT` clause determines the <<rnfb60-engine-ltt-lifecycle,data lifecycle>>:

`ON COMMIT DELETE ROWS` (default)::
Data is private to each transaction and deleted when the transaction ends.

`ON COMMIT PRESERVE ROWS`::
Data persists until the connection ends.

.Example
[source]
----
-- Create a simple LTT with default ON COMMIT DELETE ROWS
create local temporary table temp_results (
    id integer not null,
    val varchar(100)
);

-- Create an LTT that preserves data across transactions
create local temporary table session_cache (
    key varchar(50) not null,
    data blob
) on commit preserve rows;

-- Create an LTT in a specific schema
create local temporary table my_schema.work_table (
    x integer,
    y integer
);
----

[#rnfb60-ddl-ltt-alter]
=== `ALTER TABLE` (LTT)

Local Temporary Tables support the following `ALTER TABLE` operations:

[listing,subs=+quotes]
----
-- Add a column
ALTER TABLE [_ltt-schema_ <period>] _ltt-name_
  ADD [COLUMN] _column-name_ <datatype> [NOT NULL];

-- Drop a column
ALTER TABLE [_ltt-schema_ <period>] _ltt-name_
  DROP [COLUMN] _column-name_;

-- Rename a column
ALTER TABLE [_ltt-schema_ <period>] _ltt-name_
  ALTER [COLUMN] _old-name_ TO _new-name_;

-- Change column position
ALTER TABLE [_ltt-schema_ <period>] _ltt-name_
  ALTER [COLUMN] _column-name_ POSITION _new-position_;

-- Change nullability
ALTER TABLE [_ltt-schema_ <period>] _ltt-name_
  ALTER [COLUMN] _column-name_ {DROP | SET} NOT NULL;

-- Change column type
ALTER TABLE [_ltt-schema_ <period>] _ltt-name_
  ALTER [COLUMN] _column-name_ TYPE <datatype>;
----

.Example
[source]
----
create local temporary table temp_data (id integer);

alter table temp_data add name varchar(50) not null;
alter table temp_data alter column name position 1;
alter table temp_data alter column name to full_name;
alter table temp_data alter column id type bigint;
----

[#rnfb60-ddl-ltt-drop]
=== `DROP TABLE` (LTT)

[listing,subs=+quotes]
----
DROP TABLE [IF EXISTS] [_ltt-schema_ <period>] _ltt-name_
----

The same `DROP TABLE` statement is used for both regular tables and Local Temporary Tables.
If the table name matches an LTT in the current connection, the LTT is dropped.

[rnfb60-ddl-ltt-idx-create]
=== `CREATE INDEX` (LTT)

[listing,subs=+quotes]
----
CREATE [UNIQUE] [ASC[ENDING] | DESC[ENDING]] INDEX [IF NOT EXISTS]
  [_ltt-schema_ <period>] _index-name_
  ON [_ltt-schema_ <period>] _ltt-name_ (<column list>)
----

.Example
[source]
----
create local temporary table temp_orders (
    order_id integer not null,
    customer_id integer,
    order_date date
);

create unique index idx_temp_orders_pk on temp_orders (order_id);
create descending index idx_temp_orders_date on temp_orders (order_date);
create index idx_temp_orders_cust on temp_orders (customer_id);
----

[#rnfb60-ddl-ltt-idx-alter]
=== `ALTER INDEX` (LTT)

[listing,subs=+quotes]
----
ALTER INDEX [_ltt-schema_ <period>] _index-name_ {ACTIVE | INACTIVE}
----

Indexes on LTTs can be deactivated and reactivated, which may be useful when performing bulk inserts in `ON COMMIT PRESERVE ROWS` tables.

[#rnfb60-ddl-ltt-idx-drop]
=== `DROP INDEX` (LTT)

[listing,subs=+quotes]
----
DROP INDEX [IF EXISTS] [_ltt-schema_ <period>] _index-name_
----

[#rnfb60-ddl-schema]
== Schema DDL Statements
Adriano dos Santos Fernandes

With the introduction of schema, a new set of DDL statements was added for schema creation, alteration, and deletion.

These changes also mean that `SCHEMA` is no longer a synonym for `DATABASE` in some statements.
See also <<rnfb60-compat-schema-nodb>>.

[#rnfb60-ddl-schema-create]
=== `CREATE SCHEMA`

Creates a user-defined schema.

.Syntax
[listing,subs=+quotes]
----
CREATE SCHEMA [IF NOT EXISTS] _name_
  [<create schema option>...]

{CREATE OR ALTER | RECREATE} SCHEMA _name_
  [<create schema option>...]

<create schema option> ::=
    DEFAULT CHARACTER SET <character-set>
  | DEFAULT SQL SECURITY {DEFINER | INVOKER}
----

A schema can optionally have a default character set and a SQL security setting, which serve as the defaults for the objects in the schema.
When these defaults are not specified, or are later dropped, the default character set or
SQL security setting of the database are used, as in previous versions.

Unlike the automatically created `PUBLIC` schema, creating a new schema grants `USAGE` permission only to its owner, not to `PUBLIC`.

The SQL standard schema names `INFORMATION_SCHEMA` and `DEFINITION_SCHEMA` are reserved for future use as additional system schemas;
these names cannot be used for user-defined schemas.

.See also
<<rnfb60-ddl-schema-alter>>, <<<rnfb60-ddl-schema-drop>>

[#rnfb60-ddl-schema-alter]
=== `ALTER SCHEMA`

Alters configuration of a schema.

[listing,subs=+quotes]
----
ALTER SCHEMA _name_
  <alter schema option>...

<alter schema option> ::=
    SET DEFAULT CHARACTER SET <character-set>
  | SET DEFAULT SQL SECURITY {DEFINER | INVOKER}
  | DROP DEFAULT CHARACTER SET
  | DROP DEFAULT SQL SECURITY
----

[#rnfb60-ddl-schema-drop]
=== `DROP SCHEMA`

Drops (deletes) a schema.

[listing,subs=+quotes]
----
DROP SCHEMA [IF EXISTS] _name_
----

Currently, only empty schemas can be dropped.
In the future, a `CASCADE` sub-clause will be introduced, allowing schemas to be dropped along with all their contained objects.

=== `COMMENT ON SCHEMA`

Adds a comment (description) on a schema.

.Syntax
[listing,subs=+quotes]
----
COMMENT ON SCHEMA _name_ IS {NULL | <string-literal> }
----

The comment is stored in `SYSTEM.RDB$SCHEMAS.RDB$DESCRIPTION`.

[#rnfb60-ddl-drop-if-exists]
== `DROP ... [IF EXISTS]`
Adriano dos Santos Fernandes

Tracker ticket: https://github.com/FirebirdSQL/firebird/issues/4203[#4203]

Using subclause `IF EXISTS`, it's now possible to try to drop objects and not get errors when they did not exist.

.Supported statements
[listing,subs=+quotes]
----
DROP EXCEPTION [IF EXISTS] _exception_
DROP INDEX [IF EXISTS] _index-
DROP PROCEDURE [IF EXISTS] _procedure_
DROP TABLE [IF EXISTS] _table_
DROP TRIGGER [IF EXISTS] _trigger_
DROP VIEW [IF EXISTS] _view_
DROP FILTER [IF EXISTS] _filter_
DROP DOMAIN [IF EXISTS] _domain_
DROP [EXTERNAL] FUNCTION [IF EXISTS] _function_
DROP SHADOW [IF EXISTS] _shadow_
DROP ROLE [IF EXISTS] _role_
DROP GENERATOR [IF EXISTS] _generator_
DROP SEQUENCE [IF EXISTS] _sequence_
DROP COLLATION [IF EXISTS] _collation_
DROP USER [IF EXISTS] _user_ [USING PLUGIN _plugin_]
DROP PACKAGE [IF EXISTS] _package_
DROP PACKAGE BODY [IF EXISTS] _package_
DROP [GLOBAL] MAPPING [IF EXISTS] _mapping_
DROP SCHEMA [IF EXISTS] _schema_
ALTER TABLE _table_ DROP [COLUMN] [IF EXISTS] _column_
ALTER TABLE _table_ DROP CONSTRAINT [IF EXISTS] _constraint_
----

For `DROP` statements with `IF EXISTS`, DDL triggers are not fired when the object did not exist.

For `ALTER TABLE ... DROP` subclauses, DDL triggers are not fired if there are only `DROP ... IF EXISTS` subclauses and none of the columns and constraints existed.

[#rnfb60-ddl-create-if-not-exists]
== `CREATE ... [IF NOT EXISTS]`
Adriano dos Santos Fernandes

Tracker ticket: https://github.com/FirebirdSQL/firebird/issues/8062[#8062]

Using subclause `IF NOT EXISTS`, it's now possible to try to create objects and not get errors when they already exist.

.Supported statements
[listing,subs=+quotes]
----
CREATE EXCEPTION [IF NOT EXISTS] ...
CREATE INDEX [IF NOT EXISTS] ...
CREATE PROCEDURE [IF NOT EXISTS] ...
CREATE [{GLOBAL | LOCAL} TEMPORARY] TABLE [IF NOT EXISTS] ...
CREATE TRIGGER [IF NOT EXISTS] ...
CREATE VIEW [IF NOT EXISTS] ...
DECLARE FILTER [IF NOT EXISTS] ...
CREATE DOMAIN [IF NOT EXISTS] ...
CREATE FUNCTION [IF NOT EXISTS] ...
DECLARE EXTERNAL FUNCTION [IF NOT EXISTS] ...
CREATE SHADOW [IF NOT EXISTS] ...
CREATE ROLE [IF NOT EXISTS] ...
CREATE GENERATOR [IF NOT EXISTS] ...
CREATE SEQUENCE [IF NOT EXISTS] ...
CREATE COLLATION [IF NOT EXISTS] ...
CREATE USER [IF NOT EXISTS] ...
CREATE PACKAGE [IF NOT EXISTS] ...
CREATE PACKAGE BODY [IF NOT EXISTS] ...
CREATE [GLOBAL] MAPPING [IF NOT EXISTS] ...
CREATE SCHEMA [IF NOT EXISTS] ...
ALTER TABLE _table_ ADD [COLUMN] [IF NOT EXISTS] _column_ ...
ALTER TABLE _table_ ADD CONSTRAINT [IF NOT EXISTS] _constraint_ ...
----

For `CREATE` and `DECLARE` statements -- except `CREATE USER` -- where `IF NOT EXISTS` is part of the main statement, DDL triggers are not fired when the object already exists.

For the `ALTER TABLE ... ADD` subclause, DDL triggers are not fired if there are only `IF NOT EXISTS` subclauses and all columns and constraints already existed.

The engine only verifies if the name (object, column or constraint) already exists, and if so, it does nothing.
It does not try to match the definition of the existing object with the one being created.

Some objects share the same "`namespace`".
For example, there cannot be a table and a procedure -- in the same schema -- with the same name.
If there is a table `XYZ` and `CREATE PROCEDURE IF NOT EXISTS XYZ` is tried, the procedure will not be created and no error will be raised.

== Support Creation of Inactive Indices
Dimitry Sibiryakov

Tracker tickets: https://github.com/FirebirdSQL/firebird/issues/6233[#6233], https://github.com/FirebirdSQL/firebird/issues/8090[#8090]

The `CREATE INDEX` syntax was extended to allow creation of an inactive index.

.Syntax
[listing,subs=+quotes]
----

  | COMPUTED BY (<expression>) }
  [WHERE <search_condition>]
----

[#rnfb60-ddl-datatype-collate]
== Support `COLLATE` Clause in Datatype Specification
Dimitry Sibiryakov

Tracker ticket: https://github.com/FirebirdSQL/firebird/pull/7748[#7748]

Datatype specifications of string types (`CHAR`/`VARCHAR`/`NCHAR`) now also support the `COLLATE` clause, as defined in the SQL standard.

In a column definition (e.g. in `CREATE TABLE`), `COLLATE` can now syntactically occur twice: once in the datatype specification, and once at the end of the column definition.
As required by the SQL standard, an error is raised if the `COLLATE` clause is actually specified twice.

This affects (almost) anywhere a datatype can be specified, including <<rnfb60-dml-cast-collate,`CAST`>>.

[#rnfb60-ddl-alter-sql-sec]
== Alter `SQL SECURITY` State of Functions, Procedures, and Packages
Alexander Zhdanov

Tracker ticket: https://github.com/FirebirdSQL/firebird/issues/7744[#7744]

Added the ability to alter the SQL security state of a function, procedure, or package without specifying the entire body.

.Syntax
[listing]
----
ALTER PROCEDURE <name> <sql-security-option>

ALTER PACKAGE <name> <sql-security-option>

ALTER FUNCTION <name> <alter-function-option>...

<sql-security-option> ::=
    SQL SECURITY {INVOKER | DEFINER}
  | DROP SQL SECURITY

<alter-function-option> ::=
    [NOT] DETERMINISTIC
  | <sql-security-option>
----

Dropping the SQL security state will apply the SQL security configuration of the schema.

Although the syntax of `ALTER FUNCTION` allows specifying multiple conflicting SQL security options, doing so will raise an error ("`__duplicate specification of SQL SECURITY - not supported__`").

The `[NOT] DETERMINISTIC` option for `ALTER FUNCTION` is covered in <<rnfb60-ddl-alter-func-det>>.

[#rnfb60-ddl-varchar-no-length]
== Support `VARCHAR`/`VARBINARY` without explicit length
Mark Rotteveel

Tracker ticket: https://github.com/FirebirdSQL/firebird/pull/8909[#8909]

It is now possible to leave out the length for datatypes `VARCHAR`, `VARBINARY`/`BINARY VARYING` and `++{ NCHAR | NATIONAL {CHAR|CHARACTER} } VARYING++` in DDL and other places (e.g. `CAST`).
When the length is not specified, it defaults to 255.

This brings the syntax in line with the SQL standard, which specifies that these types have an implementation-defined default length.

.Examples
[source]
----
-- Column PRODUCT_NAME is defined as VARCHAR(255)
create table PRODUCT (
  ID integer generated always as identity primary key,
  PRODUCT_NAME varchar character set utf8
);

-- Converts CURRENT_TIMESTAMP to a VARCHAR(255)
select cast(CURRENT_TIMESTAMP as varchar)
from RDB$DATABASE;
----
